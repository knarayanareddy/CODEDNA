# CodeDNA review

## Scope and verdict

Prototype at `b1cf5917d51c2313b431cd8ea3be17d77856aa37`. This is a limited static sample, not an independent audit or production assessment. Runtime, builds, installs and tests were **not run**. The Python CLI, daemon, Rust scanner and VS Code extension are distinct components; interactions among them remain unverified.

The [README](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/README.md#L11-L28) describes a local style fingerprint, scanner and editor integration. [pyproject.toml:20-21](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/pyproject.toml#L20-L21) defines the CLI entry, while the [scanner](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/rust-scanner/src/main.rs#L1-L18) documents JSON subprocess IPC. A FastAPI daemon stores data locally; its actual route authorization and editor-to-daemon wiring were not traced.

## Findings ledger

- **CD-1 — High, confirmed static:** [rust-scanner/Cargo.toml:2-8](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/rust-scanner/Cargo.toml#L2-L8) repeats the same package key: `"name = \"codedna-scanner\""` appears at both lines 2 and 8. Duplicate TOML keys are invalid, blocking normal manifest parsing and scanner builds. Remove the duplicate and prove the packaged CLI can locate the built scanner, not merely compile Python.
- **CD-2 — Medium, confirmed static:** [CI:13-19](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/.github/workflows/ci.yml#L13-L19) only reaches `"- run: pip install -r requirements.txt"` and `"- run: python -m compileall -q ."`, while the README still advertises `"python -m pytest tests/ -v"` at [README:170-180](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/README.md#L170-L180). The sampled workflow does not run the existing tests or build Rust, so it can report success with CD-1 and behavior regressions. Add behavior and packaging gates.
- **CD-3 — Medium, confirmed static boundary mismatch with unverified runtime impact:** the README says `"All API endpoints require \`X-CodeDNA-Client\` header."` at [README:162](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/README.md#L162-L162) and describes `"CSRF protection - X-CodeDNA-Client header validation"` at [README:223-228](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/README.md#L223-L228). But the sampled middleware says `"For now, log unknown clients but allow them (permissive mode)"` and only checks `"X-CodeDNA-Client header is required for all API requests"` at [middleware:47-67](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/src/codedna/daemon/middleware.py#L47-L67); the app wiring separately adds `ClientValidationMiddleware` and `LocalhostOnlyMiddleware` at [app.py:91-103](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/src/codedna/daemon/app.py#L91-L103). At this SHA, loopback access and header presence are sampled, but unknown `X-CodeDNA-Client` values are still accepted, so the header is not a verified client-identity or client-registration control in permissive mode. Whether stricter deployments, caller-chain checks, browser-origin validation, or sensitive-route authorization make this acceptable remains unverified from the sampled paths; do not treat this alone as proof of exploitability.
- **CD-4 — Medium, unverified risk:** [requirements.txt:1-19](https://github.com/knarayanareddy/CODEDNA/blob/b1cf5917d51c2313b431cd8ea3be17d77856aa37/requirements.txt#L1-L19) uses version ranges such as `"fastapi>=0.109.0,<1.0.0"` and `"pytest>=7.4.0,<9.0.0"`, not a locked, hash-verified environment. Installed bytes may drift across time and machines. Establish a reproducible dependency strategy across Python and Rust.
- **CD-5 — Informational, historical CI:** the local snapshot records `"conclusion": "success"` for [run 36902569187](https://github.com/knarayanareddy/CODEDNA/actions/runs/36902569187) at this exact SHA, but the sampled workflow scope is still only the compile-only path in CD-2. Treat that run as historical evidence that the narrow workflow completed, not as evidence that Rust packaging, validated client identity, privacy behavior or the full test suite passed.

## Five-discipline assessment

**Code:** CD-1 blocks the scanner manifest; source correctness and feature-vector semantics remain untested. **Automation:** tests are present in the inventory, but the sampled workflow only checks Python compilation. **Operations:** startup, upgrade, recovery and Rust binary distribution are not verified. **Security/OWASP:** sampled code shows loopback middleware and required header presence, but in permissive mode it does not verify unknown `X-CodeDNA-Client` values as a registered caller identity. Verify binding, Origin/Host validation, authorization on every route, caller-chain assumptions, input sizes, subprocess injection, safe secret handling and local database permissions. The declared local-first model does not itself prove that code or fingerprints stay local. **UI/UX:** CLI errors and VS Code hints are the relevant interfaces, not a presumed public website. Test degraded mode and keyboard-accessible explanations; dashboard behavior was not examined.

## Blockers and owner decisions

Choose supported OS/architectures, privacy and retention guarantees, release/signing and recovery owners. Decide whether the daemon is strictly single-user/loopback and what cross-user threat model applies. Do not use style scores as proof of authorship without independent validation and a documented error rate.
